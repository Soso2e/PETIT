# Ambient Context — Turn開始時にCoreが渡す現在状況

> Status: **現行**（v0.58.0） / 関連Issue: #445（本機能）、#446（記憶の質と自動想起）、#372
>
> 実装フローの正本は [../runtime-flows.md](../runtime-flows.md) の「Ambient Context」。本書は目的・境界・判断理由を書く。

## 1. 何をするか

Brainは毎Turn、作業状況・予定・タスクを何も知らない状態で始まっていた。「今日何やればいい？」のような質問でも、まずToolを呼び、その結果を受けてもう一度モデルを呼ぶ必要があった。

`backend/ambient.py` は、Turn開始時にCoreがすでに持っている現在状況を1つのブロックにまとめて渡す。Brainはそれで足りる質問に1往復で答えられる。

| 節 | 中身 | 取得元 |
| --- | --- | --- |
| 作業 | 計測中または休憩中の作業、経過分、task_id | `work_sessions.active_session()` |
| 予定 | 今日・明日の予定（1日最大6件、総数つき） | `calendar_events_cache`（`get_schedule` と同じ同期元の絞り込み） |
| タスク | 優先度Highの未完了（最大5件、総数つき）、期限が3日以内または超過したもの（最大4件）、タスク同期の未解決件数 | `get_tasks` の既定と同じ関数、`tasks_cache` |

## 2. 境界

- **ローカルSQLiteの読み取りだけ。** ネットワーク・モデル・同期は呼ばない。予定は「最後に同期した時点のキャッシュ」であり、ブロックの冒頭にそう書く。
- **owner のTurnだけ。** ゲスト（非管理者）、Guild モード、委譲先の作業Threadには渡さない。
- **参考データであり、指示ではない。** 書き込み対象の特定、他の日付や条件、最新の確認は従来どおりToolを使う。ブロック自身にそう書いてある。人格ファイルや `brain.INSTRUCTIONS` は変えていない。
- **上限つき。** 既定1800文字（`PETIT_AMBIENT_MAX_CHARS`）。節は作業 → 予定 → タスクの順に、丸ごと入れるか落とす。
- **失敗しても会話は続ける。** 節の取得に失敗したらその節だけ落とす。知っていることが何もなければブロック自体を足さない。
- **履歴に残さない。** 会話履歴（`conversations`）には保存せず、次のTurnで作り直す。承認後の再開では、保存済みのメッセージをそのまま使い、作り直さない。
- **記録は件数だけ。** `turn_events` の `ambient_context` に文字数・所要時間・節ごとの件数を残す。予定名やタスク名は残さない。
- **切り戻し。** `PETIT_AMBIENT_CONTEXT=0` で無効になり、従来どおりToolだけで動く。

## 3. どのBrainに渡るか

| Brain | 渡し方 |
| --- | --- |
| DeepSeek / LM Studio（native Tool Loop）、Antigravity CLI、Claude Code CLI（構造化round） | 履歴の後ろ、今回の依頼の直前に user ロールの参考データとして1件 |
| Codex、Claude Code エージェントモード | `external_brain.context` の参考データJSONに `known_situation` として |

履歴の後ろに置くのは、人格と過去のやり取りという変わらない部分を先頭に保ち、Providerのプロンプトキャッシュを効かせるため。

## 4. なぜ必要か（計測）

ローカルの実行記録（直近の完了Turn）を読み取り専用で集計した結果:

- 最初に呼ばれるToolの上位は `get_work_status` / `get_tasks` / `get_schedule` など、Core内のSQLiteを読むだけのもの。Tool自体の中央値は0.02〜0.05秒。
- モデル1往復の中央値は DeepSeek で約1.4秒。Antigravity CLI のTurnは1往復で約15秒、2往復で約29秒。
- ブロックの構築は、実データのコピーで中央値約26ミリ秒、約700〜900文字。

**未確認**: 実Providerで往復数と応答時間が実際に減るかは計測していない。`turn_events` の `ambient_context` と、Turn結果の `llm_call_count` を比べれば確認できる。

## 5. 記憶を入れていない理由

当初は、発話と語句が一致する記憶も一緒に渡す設計だった。実データのコピーで試したところ、次のことが分かり、今回は入れていない。

- 有効な記憶の約9割はエピソード要約が自動で書いたもので、その多くが「その時点の状態」（時刻、当日の予定、タスク件数、同期状態、操作の記録）だった。
- 古い状態メモが現在の質問に対して上位に出る（例: 同期の失敗を尋ねると、過去の「同期は正常」が出る）。
- 本人が承認した記憶だけに絞っても、長い引き継ぎメモ1件がほとんどの発話に一致した。

記憶は従来どおり `search_memory` で取得できる。記憶の入口の見直しと自動想起は #446 で扱う。
