# タスクの追加・完了会話と優先度順

## 目的

タスクが取得上限を超えても重要なものを先に返し、会話中の明示的な追加・変更・完了報告を1ターンで書き込みまで完結させる。

## 取得順

`get_tasks`は絞り込み後、`LIMIT`を適用する前に次の順で並べる。

1. High
2. Mid / Medium
3. Low
4. 未設定・未知の値

同じ優先度では期限ありを先にし、期限が早い順に返す。

## 会話フロー

```text
ユーザー: 卒研っていうタスクやってるんだ
PETIT: そうなんだ。『卒研』っていうタスクはまだないから、追加する？
ユーザー: してほしい
PETIT: タスクを追加しました。
```

最初の発話では全状態のタスクを最大100件確認し、正規化したタイトルが完全一致する場合は重複作成を提案しない。

未登録で、ユーザーが「追加して」「してほしい」と明示した時点で`create_task`を実行する。タスクの話題を出しただけでは作成しない。

## 作成時の既定値

- `priority`: 省略時は`High`
- `category`: 省略時は既存の自動選別を使う
- `due_date`: ユーザーが日付を明示した場合だけ設定し、未指定なら期限なし

## 完了報告フロー

名前つきの完了報告は、Project ContinuityやAgentより先にSQLiteのタスク候補へ照合する。

```text
ユーザー: LiTデザインは完了した！
PETIT: 「LiTのデザイン実装」を完了にしたよ。おつかれさま！
```

`キャンプの予習も終わったわ`のような助詞`も`や自然な語尾を含む報告も、`キャンプの予習`を対象名として照合する。

判定順は次のとおり。

1. Project完了の確認中なら、その確認への返答として扱う
2. 対象名を含むTask完了報告をローカルSQLiteで候補解決する
3. 一意候補は`complete_task(task_id=...)`を即時実行する
4. 複数候補は最大5件を一度だけ提示し、番号または名前で選ばせる
5. 完了済みなら再書き込みせず、その状態を返す
6. 0件なら別名を短く聞く
7. 明示的なProject完了や対象名のない「終わった」はProject Continuityへ渡す

この経路ではLLMと反復`get_tasks`を使わない。候補解決と実行結果を決定論的に扱い、候補を確定できなかった責任をTool上限メッセージとしてユーザーへ返さない。対象名を含む完了報告を、単に`終わった`を含むという理由だけでProject名不足へ強制フォールバックさせない。

## 安全境界

- 未登録タスクの提案だけでは書き込まない
- 作成・変更・完了は、ユーザーの明示指示がある場合だけToolをcallする
- 対象が複数または不明なら書き込まず、短く対象を聞く
- `complete_task`が失敗した場合は完了済みと答えず、未反映を明示する
- 既存の引数検証、エラー処理、Notion同期キューを維持する
- 予定追加、BRAIN編集、外部紐付け、破壊的操作などの確認待ちは従来の承認APIを維持する
