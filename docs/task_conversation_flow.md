# タスクの追加・完了会話と優先度順

## 目的

タスクが取得上限を超えても重要なものを先に返し、会話中の追加・完了報告を自然な確認から書き込みまで完結させる。

## 取得順

`get_tasks`は絞り込み後、`LIMIT`を適用する前に次の順で並べる。

1. High
2. Mid / Medium
3. Low
4. 未設定・未知の値

同じ優先度では期限ありを先にし、期限が早い順に返す。

## 会話フロー

```text
ユーザー: 卒研っていうタスクやってるんだ
PETIT: そうなんだ。『卒研』っていうタスクはまだないから、追加する？
ユーザー: してほしい
PETIT: タスクを追加しました。
```

最初の発話では全状態のタスクを最大100件確認し、正規化したタイトルが完全一致する場合は重複作成を提案しない。

未登録時は`create_task`の確認待ち操作を作る。ブラウザでは最新の確認待ち操作に対する短い肯定・否定を、確認ボタンと同じ決定として処理する。

## 作成時の既定値

- `priority`: 省略時は`High`
- `category`: 省略時は既存の自動選別を使う
- `due_date`: ユーザーが日付を明示した場合だけ設定し、未指定なら期限なし

## 完了報告フロー

名前つきの完了報告は、Project ContinuityやAgentより先にSQLiteのタスク候補へ照合する。

```text
ユーザー: LiTデザインは完了した！
PETIT: おつかれさま！「LiTのデザイン実装」だね。完了に反映していい？
ユーザー: うん
PETIT: 「LiTのデザイン実装」を完了にしたよ。おつかれさま！
```

判定順は次のとおり。

1. Project完了の確認中なら、その確認への返答として扱う
2. 対象名を含むTask完了報告をローカルSQLiteで候補解決する
3. 一意候補は`complete_task(task_id=...)`の確認を表示する
4. 複数候補は最大5件を一度だけ提示し、番号または名前で選ばせる
5. 完了済みなら再書き込みせず、その状態を返す
6. 0件なら別名を短く聞く
7. 明示的なProject完了や対象名のない「終わった」はProject Continuityへ渡す

この経路ではLLMと反復`get_tasks`を使わない。候補解決、確認、実行結果の返答を別の状態として扱い、候補を確定できなかった責任をTool上限メッセージとしてユーザーへ返さない。

## 安全境界

- 未登録タスクの提案だけでは書き込まない
- 完了候補が一意でも、確認前には`Done`へ変更しない
- 確認待ち操作と既存の承認APIを通して実行する
- 複数の確認待ちがある場合、ブラウザの短い返答は最新の有効な操作だけを対象にする
- 確認待ちがない場合、通常の会話として送信する
- 既存の確認TTL、エラー処理、Notion同期キューを維持する
